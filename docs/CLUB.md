# Bread Club selection runbook

A weekly cadence for getting members their loaf:

1. **Tuesday — publish the drop in Sanity.** Create or update the drop doc. Status: `announced`. Add `lineItems` for every flavor that will be in this batch. Leave each `quantity` at the *total* you'll bake; the storefront and the checkout API automatically subtract member picks.
2. **Tuesday — send magic links.** Two modes:

   **Dry-run (default):** prints `email\tURL` lines you can paste into any email tool.
   ```bash
   npm run club:emails                  # auto-detects the announced drop
   ```

   **Send via Resend:**
   ```bash
   npm run club:emails -- --send        # mails each member their magic link
   ```
   Each row prints `[ok] email` on success or `[fail] email\treason` on failure. Failures don't stop the rest. The script uses `RESEND_API_KEY` + `FROM_EMAIL` from `.env.local`. (Until you verify a sending domain in Resend, only your account email will deliver — the rest will `[fail]` with a 422.)
3. **Wednesday night — close the selection window.** In Sanity Studio, change the drop's status from `announced` → `open`. Public orders are now open. The `/club` page is read-only at this point: members who didn't pick are flagged on the bake list.
4. **Friday — bake.** Open `/admin/club`, log in with your `BAKER_TOKEN` once (cookie is remembered for 30 days), and you'll see the bake list: each member's name, phone, shipping address (pulled from Stripe), and chosen flavor, plus a per-flavor tally. Print or pull up on your phone at the oven. Log out from the link in the corner when you're done on a shared device.
5. **Saturday — pickup.** Sold-out happens when public stock + member picks all clear. Flip status to `closed` once done.

## How public availability is calculated

For each line item:
- `public_remaining = max(0, quantity - count(memberSelection docs for that slug))`

This means a member's selection immediately removes one loaf from public stock. There is **no separate member bucket** — selections are the reservation.

## Failure modes

- **Member missed the window.** They're auto-assigned the default loaf (`site.breadClub.defaultLoafSlug`, currently `classic`) with local pickup. It shows on the bake list flagged "(default — never picked)" and on their own `/club` page as a locked-in pick. No baker action needed. (If the default loaf isn't in the drop's line items, the member shows as no-pick and the baker handles it manually.)
- **Member cancels mid-cycle.** Today: their next link is just never generated by `club:emails`. Their last selection (if any) sticks until the drop closes.
- **Skip-a-week.** Pause the Stripe subscription for that member-week in the dashboard. (Automating this is a future task.)
- **Token leak.** Rotate `CLUB_LINK_SECRET` in `.env.local`; every outstanding link instantly becomes invalid.
- **Two members race for the last of a flavor.** The `/api/club/select` endpoint re-counts current selections before writing and returns a 409 if claims would exceed the line's quantity — second click loses.

## How membership is tracked

Stripe is the source of truth. The webhook at `/api/webhooks/stripe` listens for `customer.subscription.created`, `customer.subscription.updated`, and `customer.subscription.deleted`, and mirrors the active subscription into a Sanity `member` document. The doc's `_id` is the Stripe customer id, so a single customer always upserts to the same record.

Anywhere we need to know "who's a member?" we read from Sanity, not from Stripe. The `npm run club:emails` script reads the cache first; if it's empty (webhook never fired yet, fresh setup, etc.), it falls back to a live `stripe.subscriptions.list` call so the script still works during bootstrap.

To sync existing subscribers into the cache after first wiring the webhook: trigger a `customer.subscription.updated` event for each member from the Stripe dashboard (Subscriptions → click one → ⋯ → "Send test webhook"), or just wait for the next billing cycle — the webhook fires on invoice events too.

## Seat cap (12 members)

`site.breadClub.seats` (currently 12) is the ceiling. Enforcement is two-layered:

- The `/bread-club` page reads the Sanity member count and either shows the Join form (with "X of 12 spots left") or — when full — a waitlist mailto.
- `/api/bread-club` re-checks the count server-side before opening Stripe Checkout, so two browser tabs racing past each other can't blow past 12.

Adjust the cap in `src/lib/site.ts`. Demo mode (no Sanity) treats the club as "always open" because the cache isn't readable.

## Duplicate-subscription prevention

Sign-up on `/bread-club` requires an email up front. `/api/bread-club` checks that email against the Sanity member cache before opening Stripe Checkout:

- If the email already has an `active`, `trialing`, or `past_due` subscription, the route returns `{ alreadyMember: true }` with a friendly message pointing the user at their Stripe payment receipt for the manage-subscription link. **Stripe Checkout never opens — no double charge possible.**
- Otherwise the route pre-fills + locks `customer_email` in Checkout, so the email the user just typed is the email Stripe records against the new subscription.

If a duplicate ever slips through anyway (e.g., a member subscribes from two devices simultaneously with cache lag), the webhook will create two `member` docs (different Stripe customer ids). Use the Stripe Dashboard to refund the duplicate charge + cancel the duplicate subscription. The cancellation webhook will then mark the duplicate `member` doc as `canceled`.

## Cancellation, pause, and card updates (Stripe Customer Portal)

Members hit the **Manage subscription** link at the bottom of their `/club/[dropId]` page. That POSTs to `/api/club/portal`, which:

1. Re-verifies the magic-link token (so only the member themselves can open the portal)
2. Looks up their Stripe customer id from the Sanity member cache
3. Creates a Stripe-hosted Customer Portal session and redirects there
4. Member updates card / pauses / cancels in Stripe's UI
5. Returns to their `/club/[dropId]` page

**One-time setup in Stripe**: Dashboard → Settings → Customer Portal → **Activate**. You can also configure what's allowed (cancel immediately vs. at period end, allow pause, allow card update, etc.) on the same page. The defaults are sane.

When a member cancels through the portal, Stripe fires `customer.subscription.deleted` → our webhook updates the `member` doc to `subscriptionStatus: "canceled"` + stamps `canceledAt`. The cap-check then sees one fewer active member and the seat re-opens automatically.

## Shipping cost collection

When a member toggles **📦 Ship** on the picker, `/api/club/select`:

1. Looks up their Stripe customer id from the Sanity `member` cache.
2. Creates a **pending Stripe invoice item** for `site.breadClub.shipSurchargeCents` (currently $12.00) — no `invoice`/`subscription` set, so Stripe automatically sweeps it onto their **next** subscription invoice. The item id is stored on the `memberSelection` doc (`shipInvoiceItemId`).
3. If they switch back to **📍 Pickup**, the pending invoice item is deleted and the field cleared — no charge.

Idempotent per (drop, member): re-confirming ship doesn't stack a second charge. The member sees `+$12.00` on the ship toggle and a line in their confirmation email; the bake list shows the total shipping auto-billed this cycle.

Edge cases:
- **Member not yet in the cache** (webhook hadn't synced when they picked) → selection still saves but shipping is NOT billed; a `[club/select]` warning is logged for manual reconciliation.
- **Switch to pickup after the item already hit a finalized invoice** (a billing cycle landed mid-window) → deletion fails, logged; refund manually in the Stripe dashboard. Rare at this scale.
- Adjust the fee in `src/lib/site.ts` → `breadClub.shipSurchargeCents`. Keep it in step with the public `ca-priority` shipping option.
